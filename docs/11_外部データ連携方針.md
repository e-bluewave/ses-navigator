# 外部データ連携方針

- 対象プロジェクト: SES Navigator
- 作成日: 2026-09-27
- ステータス: 方針案
- 関連資料: `docs/10_エンジニア案件サイト調査.md`

## 1. 目的

SES Navigatorを、単なる案件管理システムではなく、

> 外部案件情報・自社案件情報・技術者情報を統合し、AIで案件と技術者をマッチングするSES営業支援基盤

へ発展させるための外部データ連携方針を定める。

## 2. 基本原則

### 原則1: MVP1の中心機能を外部収集にしない

MVP1では、まず以下を完成させる。

```
案件登録
  ↓
案件情報の構造化
  ↓
技術者登録
  ↓
技術者情報の構造化
  ↓
AIマッチング
  ↓
マッチ理由の提示
  ↓
営業による確認
  ↓
提案
```

外部サイトの自動収集はMVP1の必須条件にしない。

### 原則2: 外部サイトを「案件ソース」と「技術者ソース」に分ける

#### 案件ソース

- SES JOB LINK
- SES BASE
- SESクラウド
- フリーランススタート
- FreelanceBox
- フリーランスHub
- エンジニアスタイル
- レバテックフリーランス
- Midworks
- その他のフリーランス/SES案件サイト

#### 技術者ソース

- Findy
- LAPRAS
- paiza
- Green
- Forkwell
- 転職ドラフト
- その他のエンジニア特化/スカウトサービス

案件と技術者を同一データモデルとして扱わない。

## 3. 外部データ連携の優先順位

原則として次の順序で検討する。

1. **正式API**
2. **公式なデータ提供/提携**
3. **RSS/XML/Feed等の公式提供**
4. **案件企業・BPからの直接データ提供**
5. **ユーザーが登録した案件URLのAI解析**
6. **利用許諾が確認できた場合の取得処理**
7. **その他の自動取得**

無許可スクレイピングを前提とする設計は禁止する。

## 4. 最初に実装する候補: URL → AI構造化

外部APIが利用できないサイトについては、MVP2以降で以下を検討する。

```
営業が外部案件URLを登録
        ↓
URL取得
        ↓
本文/構造化データを解析
        ↓
AIで案件項目を抽出
        ↓
共通案件スキーマへ変換
        ↓
重複候補を検索
        ↓
営業が確認
        ↓
案件DBへ登録
```

AI抽出結果を無条件に公開/提案へ利用せず、必要に応じて営業確認を挟む。

## 5. 共通案件データモデル

外部サイトごとに異なる項目名を、そのままアプリ全体へ持ち込まない。

最低限、次のような共通項目へ正規化する。

```
source_site
source_job_id
source_url

title
description

required_skills[]
preferred_skills[]

role
industry

location
remote_type

unit_price_min
unit_price_max
unit_price_type

start_date
duration

working_days
working_hours

contract_type
contract_chain

interview_count

company_name
agency_name

status

first_seen_at
last_seen_at
closed_at

raw_source_hash
```

実際のスキーマ追加は既存DB設計との整合性を確認してから行う。

## 6. 重複案件の考え方

同一案件が複数サイト・複数企業経由で掲載される可能性がある。

そのため、

```
source_site + source_job_id
```

だけでは「同一案件」の判定にならない。

将来的には以下を組み合わせて重複候補を判定する。

- 案件タイトル
- 必須スキル
- 勤務地
- リモート条件
- 単価レンジ
- 開始日
- 業務内容
- 商流
- 発注元/掲載元
- テキスト類似度
- AIによる同一案件判定

ただし、AI判定だけで既存案件を自動削除しない。

## 7. 案件のライフサイクル

外部案件は「登録したら終わり」ではない。

```
discovered
   ↓
normalized
   ↓
review_pending
   ↓
active
   ↓
stale
   ↓
closed
```

など、外部ソースの状態を管理できるようにする。

特に、

- first_seen_at
- last_seen_at
- status
- closed_at

を保持し、「以前見つけた案件が現在も有効か」を判定できる構造を優先する。

## 8. 技術者データの扱い

外部の技術者プロフィールを取得する場合は、案件情報以上に慎重に扱う。

最低限、

- 情報源
- 取得日時
- 公開情報かどうか
- 利用目的
- 保存可否
- 削除/更新条件
- 本人の同意が必要か
- 外部サービスの利用規約

を確認する。

GitHub、技術ブログ、スキルチェック等の公開情報を扱える場合でも、「公開されている = SES Navigatorが自由にデータベース化できる」とは判断しない。

## 9. スカウトサービスについて

Findy、LAPRAS、paiza、Green、Forkwell等のスカウト型サービスは、案件情報だけでなく技術者のスキル・技術実績を扱う点が特徴である。

SES Navigatorでは、これらを直接コピーすることを目的とせず、

> 「案件要件に対して、技術者のどの経験が一致するかを説明する」

というAIマッチング機能の設計参考として利用する。

## 10. API連携時の実装原則

正式APIを利用できる場合でも、以下を確認する。

1. API利用資格
2. 認証方式
3. レート制限
4. データ保存期間
5. 再配布可否
6. 表示義務
7. 出典表示
8. キャッシュ条件
9. 削除要求への対応
10. 商用利用条件

APIがあることだけを理由に、本番DBへの恒久保存を決定しない。

## 11. スクレイピングについて

技術的にHTMLを取得できることと、サービスとして取得してよいことは別問題である。

実装前に、

- 利用規約
- robots.txt
- API規約
- 著作権
- 個人情報
- 不正アクセス/アクセス制限
- CAPTCHA
- ログイン後情報
- サイトへの負荷

を確認する。

以下は禁止する。

- ログイン情報を使った無許可自動取得
- CAPTCHA等の回避
- アクセス制限の回避
- 利用規約に反する大量取得
- 出典を隠した外部データの再配布

## 12. 段階的なロードマップ

### MVP1

**外部自動収集なし**

- 自社案件登録
- 技術者登録
- AI案件構造化
- AI技術者構造化
- AIマッチング
- 推薦理由
- 営業確認

### MVP2

**URL → AI抽出**

- 外部案件URL登録
- ページ解析
- AIによる案件項目抽出
- 正規化
- 重複候補提示
- 営業確認
- 案件DB登録

### MVP3

**正式API/提携データの自動連携**

- API認証
- 定期取得
- 差分更新
- 重複排除
- 失効検知
- 取得ログ
- エラー監視
- 利用制限監視

### 将来

**案件・技術者情報統合基盤**

```
外部案件
  +
自社案件
  +
外部/自社技術者情報
       ↓
正規化
       ↓
重複排除
       ↓
スキル標準化
       ↓
AIマッチング
       ↓
推薦理由
       ↓
営業アクション
       ↓
提案結果
       ↓
学習/改善
```

## 13. SES Navigatorの差別化ポイント

外部サイトと同じ「案件検索サイト」を作ることを目的としない。

SES Navigatorの中心価値は、

> **案件を見つけることではなく、「この案件に誰を提案すべきか」を営業が短時間で判断できること**

とする。

したがって外部サイト連携の評価基準は、

- 案件数が多いか
- APIがあるか

だけではなく、

- 自社技術者とのマッチングに使えるか
- 案件情報を構造化できるか
- 重複を排除できるか
- 案件更新を検知できるか
- 営業の提案時間を削減できるか

を重視する。

## 14. 連携候補の評価基準

新しい外部サービスを追加する場合は、以下で評価する。

| 評価項目 | 内容 |
|---|---|
| 案件量 | 現在有効な案件がどれだけあるか |
| 案件品質 | SES Navigator対象案件との適合度 |
| 技術情報 | スキル情報が構造化されているか |
| 更新性 | 案件終了/変更を検知できるか |
| API | 正式APIの有無 |
| 利用条件 | 商用利用・保存・再配布条件 |
| 重複 | 他ソースとの重複率 |
| AI抽出適性 | URLから構造化しやすいか |
| 営業価値 | 提案候補を増やせるか |
| 開発コスト | 実装・保守コスト |

## 15. 開発時のルール

外部連携を実装する場合は、既存のSES Navigator開発ルールに従い、

1. まず現在のMainと既存仕様を確認する
2. 対象サービスの最新仕様/規約を確認する
3. 連携方式を決定する
4. DB変更が必要ならmigrationを設計する
5. 実装
6. テスト
7. lint
8. type-check
9. build
10. 実データまたは検証用データで確認
11. 1実装単位/1migration = 1commit
12. レビュー後にMainへ反映

とする。

外部サービス仕様を推測して実装しない。

## 16. 今回の調査結果からの当面の決定

- MVP1に外部サイト自動収集を追加しない。
- 外部案件URLをAIで構造化する方式をMVP2候補とする。
- API/正式提携が可能なサービスはMVP3候補とする。
- 無許可スクレイピングを基本方式にしない。
- 案件ソースと技術者ソースを分離する。
- source_site / source_job_id / source_url / first_seen_at / last_seen_at / status を外部案件管理の基本項目とする。
- 「掲載件数」を「有効案件数」と同一視しない。
- 外部データ連携は、案件数よりもAIマッチングへの寄与を評価する。
- 新規連携先を追加するたびに、利用規約/API条件をその時点で再確認する。

## 17. 更新ルール

この方針は、外部サービスの仕様・規約・API条件が変更された場合に更新する。

特にAPI、スクレイピング、個人情報、データ保存/再配布に関する判断は、過去の調査結果をそのまま適用せず、実装時点の公式情報を再確認する。
