# 11_テスト設計

## 1. 目的

SES NavigatorのMVPについて、機能、データ、認証・認可、AI、非機能要件が設計どおり動作することを継続的に確認するため、テスト方針、責任範囲、環境、合格条件、証跡を定義する。

本書は実装開始時の基準であり、具体的なテストケース、フィクスチャ、実行コマンドは実装とともにリポジトリへ追加する。

## 2. 基本原則

1. テナント越境、権限迂回、秘密情報漏えいを最優先で防ぐ。
2. 正常系だけでなく、境界値、異常系、競合、再試行、取消を確認する。
3. RLS、GRANT、API、アプリケーションの各層を独立して検証する。
4. AI出力の完全一致ではなく、構造、根拠、禁止事項、業務制約を検証する。
5. 本番データ、実在する個人情報、秘密情報をテストデータへ使用しない。
6. 再実行可能で相互依存の少ないテストを優先する。
7. 不具合修正時は再現テストを追加し、同種の回帰を防ぐ。
8. 手動確認は目的と証跡を明記し、自動化可能なものは段階的にCIへ移す。
9. テスト失敗を無効化してリリースせず、例外は期限・責任者・代替統制を記録する。
10. 本番反映前にロールバックと復旧手順を確認する。

## 3. 適用範囲

### 3.1 MVP対象

- React / TypeScriptフロントエンド
- Vercel FunctionsまたはSupabase Edge Functions
- PostgreSQL 16、Migration、RLS、RPC、View
- Supabase Auth、Storage、Realtime
- 案件、技術者、会社、提案、面談、契約、請求等の主要業務
- ファイル取込と処理
- AI抽出、マッチング説明、提案文、面談要約、営業支援
- ジョブ、Outbox、通知、監査、冪等性
- ローカル、CI、Staging、本番前確認

### 3.2 MVP外

- 本番環境を使う破壊的負荷試験
- 実在顧客データを用いるAI評価
- 未採用のEmbedding・自律エージェント機能
- 外部サービス提供者自身の内部品質保証

MVP外の機能を実装対象へ追加する場合は、本書の対象とリリースゲートも更新する。

## 5. テスト環境

|環境|用途|データ|外部連携|
|---|---|---|---|
|Local|開発・高速確認|固定Seed・Fixture|原則Mock|
|CI|自動回帰|実行ごとに初期化|MockまたはSandbox|
|Staging|統合・E2E・受入|架空データ|Sandbox|
|Production|Smoke・監視|本番データ|本番。破壊操作禁止|

- LocalとCIはMigrationを001から順に適用し、必要に応じて `supabase/seed.sql` を使用する。
- テスト間で状態を共有せず、固定UUIDまたはテストごとの識別子でデータを分離する。
- 日時依存処理はClockを注入し、JST、UTC、月末、閏日、DSTを明示して検証する。
- AI、メール、外部Webhookは通常Mockを使い、実プロバイダー確認はStagingの限定ケースにする。
- SecretはCI Secret管理を使用し、ログ、Fixture、Snapshotへ含めない。

### 6.1 必須パターン

- Tenant A / Tenant B

- System Admin、Tenant Admin、Manager、Sales、閲覧限定、権限なし

- 同時更新と重複リクエスト
- 日本語、英語、記号、長文、文字化け候補

### 6.2 取扱い

- 架空の会社名、氏名、メールアドレスを使用する。
- パスワード、JWT、API Key、Service Role Keyをリポジトリへ保存しない。
- Snapshotや失敗ログに個人情報・AI原文を残さない。
- 本番障害の再現データは匿名化・最小化し、利用期限と削除確認を設ける。
- Seedは開発開始用、Fixtureはテストの期待条件用として責務を分離する。

## 8. DB・Migrationテスト

### 8.1 Migration

1. 空DBへ001から最新まで適用できる。
2. 適用後のSchemaが期待する構造と一致する。
3. Migration適用後にSeedを再実行できる。
4. 過去Migrationを変更せず、新しい変更を次番号へ追加する。
5. 破壊的変更にはデータ移行、影響確認、ロールバック方針がある。
6. 本番相当データ量でLock時間とTimeoutを確認する。

### 8.2 データ完全性

- PK、FK、複合FK、UNIQUE、CHECK、NOT NULL
- Tenantを跨ぐ参照の拒否
- 論理削除・有効期間・履歴の整合
- 状態遷移外の更新拒否
- 金額・数量・期間の境界値
- 更新日時、作成者、監査情報
- 競合更新時の `row_version` 検証

### 8.3 RLS・権限マトリクス

各保護対象について、少なくとも次を確認する。

|Actor|同一Tenant・許可組織|同一Tenant・対象外組織|他Tenant|期限切れ権限|
|---|---|---|---|---|
|anon|拒否|拒否|拒否|拒否|
|authenticated・権限あり|許可|Policyどおり|拒否|拒否|
|authenticated・権限なし|拒否|拒否|拒否|拒否|
|service_role|限定RPCのみ|限定RPCのみ|対象不一致を秘匿|限定RPCのみ|

SELECT、INSERT、UPDATE、DELETEを別々に確認する。フロントエンドの非表示だけを認可対策としない。

限定Viewの実環境回帰は`pnpm security:data-api`で実行する。User Aは権限あり、User Bは権限なしとして、6 Viewの匿名拒否、許可Tenantの1件取得、権限なしの0件取得、返却列の完全一致を合計18件確認する。CIでは秘密情報を必要としない`pnpm security:data-api:check`で判定ロジックを回帰する。

Service Role境界は`pnpm security:service-rpc`で実行する。利用者向け6 Viewの403拒否を先に確認し、合格した場合だけ限定RPCのanon・authenticated拒否、許可5リソースの完全一致、存在しない対象と別Tenant対象の404秘匿を合計19件確認する。CIでは`pnpm security:service-rpc:check`で判定・秘匿ロジックを回帰する。

Data API公開設定は`pnpm security:supabase-config`で検証する。公開スキーマは`public`・`graphql_public`・`app`、追加search_pathは`public`・`extensions`に完全一致させ、`audit`・`private`・`integration`・`storage`の混入と1,000件を超える返却上限を拒否する。Dashboard実値は`SESN_REMOTE_EXPOSED_SCHEMAS`で照合する。

Data APIスキーマルーティングは`pnpm security:data-api-routing`で検証する。`/rest/v1`を呼ぶ全API実装が共通ヘッダー関数を使用することを静的検査し、共通関数の単体テストで通常リレーションを`app`、`/rpc/`を`public`へ振り分けることを確認する。

実環境のスキーマ・書込み境界は`pnpm security:data-api-runtime`で検証する。anonの`app`リレーション・`public` RPC拒否、authenticatedの`app`読取り・`public`認証補助RPC許可、レビュー済み`projects`更新面の0件更新成功、未許可`contracts`更新とService Role限定RPCの拒否、`audit`スキーマ非公開を合計8件確認する。更新対象には実行時生成UUIDを使い、事前に0件を確認した場合だけPATCHするためデータは変更しない。CIでは秘密情報を使わない4件のランナーロジックテストを実行する。

実環境の総合確認は`pnpm security:data-api:all`で実行する。必要な7環境変数とSecret key種別を通信前に検査し、限定View 18件、Service Role・限定RPC 19件、スキーマ・書込み境界8件を順番に実行して45件を集計する。失敗時は後続ステージを停止し、秘密情報を含まないコンポーネント別結果を出力する。CIでは4件の統合・停止制御ロジックを回帰する。

ブラウザ秘密情報境界は`pnpm security:client-secrets`で検証する。`apps/web`のソース、環境変数例、生成済み`dist`を走査し、Service Role・Supabase Secret key・`VITE_`公開変数へ置かれたSecretを拒否する。検出結果にはファイル・行・ルールだけを出し、秘密値そのものをログへ含めない。CIでは判定ロジックを単体回帰し、ビルド後の成果物も走査する。

直接書込みGRANTは`pnpm security:data-api-writes`で検証する。全Migrationの明示的な表GRANT・REVOKEを番号順に適用し、authenticatedの書込み権限がレビュー済み10テーブルと操作種別に完全一致すること、anonの書込みが0件であること、Service Roleが`public`リレーションへ直接書き込めないことを確認する。CIでは現在のMigration実体と5件のガード回帰テストを両方実行する。

RPC公開面は`pnpm security:data-api-rpcs`で検証する。APIソースから`/rpc/<name>`と共通RPCヘルパーの固定名を抽出し、全MigrationのFunction GRANT・REVOKEを適用順に再構成する。authenticatedはAPI利用中81件とレビュー済み未接続2件だけ、Service Roleは限定1件だけ、anon・PUBLICは0件であることを確認する。CIではMigration実体と6件のガード回帰テストを両方実行する。

## 12. E2E・受入テスト

### 12.1 重要シナリオ

1. 招待された営業利用者がログインし、所属Tenantだけを閲覧する。
2. 案件を登録し、技術者を検索して候補を確認する。
3. 経歴書を取り込み、AI候補を人が修正・承認する。
4. マッチング根拠を確認し、提案文を生成・編集・承認する。
5. 提案から面談、契約、参画へ正しい状態で遷移する。
6. 権限のない利用者が機密・契約・財務・監査情報を取得できない。
7. 管理者が利用者を停止し、そのセッションが利用不能になる。
8. AI・外部サービス障害中も手動の中核業務を継続できる。

### 12.2 受入基準

- 業務担当者が主要シナリオを完了できる。
- 表示と保存結果が一致する。
- 二重登録・二重送信が発生しない。
- 権限外データの存在を推測できない。
- 重要操作が監査可能である。
- エラー時に利用者が次の行動を判断できる。

## 13. AIテスト

### 13.1 対象

- `resume.extract`
- `project.extract`
- `match.explain`
- `proposal.compose`
- `interview.summarize`
- `sales.suggest`

### 13.2 評価

|区分|指標|
|---|---|
|構造|JSON Schema適合率、必須項目充足|
|正確性|適合率、再現率、原文との一致|
|根拠|根拠付与率、根拠一致率|
|安全性|入力外断定、禁止項目、機密漏えい|
|耐性|Prompt Injection、長文、矛盾、欠損|
|運用|承認率、編集率、却下率|
|非機能|Latency、Token、費用、失敗率|

モデル出力の文字列完全一致は原則使用しない。決定的なValidatorと評価Rubricを組み合わせ、旧公開版と比較する。

### 13.3 初期リリースゲート

- 必須ケースのJSON Schema適合率: 100%
- Tenant越境、Secret漏えい、重大な機密漏えい: 0件
- 人の承認を迂回する経路: 0件
- Injectionケースで上位指示と出力契約を維持: 100%
- 必須事実の用途別目標値: 評価セット確定時に設定
- 品質、費用、Latency: 採用モデル決定時に用途別設定
- 前公開版に対する重大な品質回帰: 0件

未確定の数値を推測で本番基準にせず、評価セット・モデル・実測値とともに確定する。

## 14. セキュリティテスト

- OWASP Top 10を基準とした入力・認証・アクセス制御
- IDを差し替えた水平・垂直権限昇格
- Tenant、組織、担当、共有、有効期限の組合せ
- Data APIの公開Schema、Table、View、RPC、GRANT
- Service Role Keyがクライアントへ含まれないこと
- SQL Injection、XSS、CSV Injection、Path Traversal
- Uploadの拡張子、MIME、容量、Malware、署名URL期限
- Prompt InjectionとAI出力の自動実行防止
- Webhook署名とReplay防止
- Secret scanning、依存関係・コンテナ脆弱性
- ログ・監査・エラーへの機密情報混入
- Rate Limitと大量リクエスト

重大・高リスクの未解決脆弱性がある場合はリリースしない。

## 15. 性能・信頼性テスト

実装後、想定利用量とStaging実測に基づき目標値を確定する。少なくとも次を計測する。

- 一覧・検索のp50 / p95 / p99
- RLS付きクエリと限定View / RPC
- 大量案件・技術者・経歴書での検索
- ファイル取込と非同期処理
- AIジョブのQueue待ち、実行、Timeout
- 同時更新、Lock、Deadlock、楽観ロック
- Outbox・Webhookの再送と重複抑止
- Rate Limit、Circuit Breaker、縮退動作
- DB接続数、CPU、Memory、Storage、費用

性能基準を満たすために認可を弱めない。改善前後で実行計画と結果を保存する。

## 16. 障害・復旧テスト

- DB接続断、外部API Timeout、429、5xx
- Job Worker中断と再開
- 同一イベントの重複配送
- AI構造不正と限定再試行
- Storage障害・ファイル検査失敗
- Migration失敗時の停止・復旧
- 直前リリースへのロールバック
- DB・Storageバックアップからの復元
- RPO / RTOの実測
- AI停止時の手動業務継続

復元テストは本番を上書きしない隔離環境で行い、実行日時、所要時間、欠損、担当者を記録する。

## 18. 不具合管理

|Severity|例|リリース判断|
|---|---|---|
|Critical|Tenant越境、Secret漏えい、データ破壊、認証迂回|必ず停止|
|High|主要業務不能、重大な権限不備、復旧不能|原則停止|
|Medium|回避策がある機能不備、限定的な不整合|責任者判断|
|Low|軽微な表示、文言、操作性|バックログ可|

不具合には再現条件、期待値、実結果、環境、証跡、影響、原因、修正、回帰テストを記録する。

## 19. リリース判定

次をすべて満たした場合にリリース可能とする。

- 必須CI Checkが成功している。
- Critical / Highの未解決不具合が0件である。
- 主要E2Eと受入テストが合格している。
- Tenant越境、権限迂回、Secret漏えいが0件である。
- Migration、バックアップ、ロールバックを確認済みである。
- AI変更時はAIリリースゲートを満たしている。
- 監視、Runbook、担当、連絡先が準備されている。
- 既知のMedium / Lowは影響、回避策、期限、責任者を承認済みである。

## 20. 証跡

各実行で可能な範囲で次を保存する。

- Commit SHA、Branch / PR、実行日時
- 環境、Migration番号、Schema版
- Test suite、合格・失敗・Skip件数
- 失敗内容と再実行結果
- AIのPrompt・Schema・モデル版
- 性能計測条件と結果
- 手動確認者と承認
- 秘密情報を除いたReport・Artifact

証跡の保持期間と保管先は `docs/12_運用設計.md` で定義する。
