# RB-018 監視・通知

## 目的

SES Navigatorの本番運用に必要なエラー、DB、RLS、ジョブの監視対象と通知・一次対応を定義する。

## 方針

監視製品は現時点で固定しない。アプリケーション、Supabase/PostgreSQL、ジョブ実行基盤から必要なシグナルを取得できることを要件とし、後から監視製品を差し替えられる構成とする。

## 必須監視項目

- アプリケーションエラー
- 遅いSQL
- DB接続数・接続率
- DB容量
- lock wait / long transaction
- RLSを含むクエリ負荷
- ジョブ滞留件数・最古ジョブ経過時間

## 初期しきい値

初期値は本番前の技術ベースラインとして以下を置く。BA-014負荷試験とStaging実測で必ず調整する。

- slow SQL: 1000ms以上を観測対象
- DB connection warning: 70%
- DB connection critical: 85%
- DB capacity warning: 70%
- DB capacity critical: 85%
- lock wait warning: 10秒
- job backlog warning: 100件
- oldest job warning: 15分

これらは契約上のSLAではなく、異常検知開始点である。

## Severity

### critical

業務継続・データ整合性・認証・財務等への即時影響がある状態。即時通知し、担当者が一次切り分けを開始する。

### warning

容量逼迫、遅延増大、接続率上昇、job滞留等、放置するとcriticalへ進む状態。通知し、同営業日内に確認する。

### info

運用記録や回復通知等。原則として緊急対応不要。

## 通知要件

- critical/warningは通知する。
- 同一事象の重複通知を抑止する。
- 回復時の通知を行う。
- 各alert ruleにはownerを設定する。
- 通知先・実サービス名は環境別運用台帳で管理し、公開GitHubへ機密情報を置かない。

## セキュリティ

alert・ログへ以下を出力しない。

- password / token / API key / JWT
- Production Project Ref等の不要な識別子
- 個人情報や経歴書本文
- SQLのbind parameter値

SQL監視ではquery shape、fingerprint、duration等を優先する。

## 一次対応

1. alert発生時刻、severity、対象componentを確認する。
2. 同時刻のdeploy、migration、batch、外部障害を確認する。
3. DBの場合は接続率、active query、lock、long transaction、容量を確認する。
4. RLS負荷の場合は対象query shape、tenant scope、実行計画、件数を確認する。
5. job backlogの場合はworker health、失敗率、最古job、再試行を確認する。
6. 復旧後、回復通知と原因・再発防止を記録する。

## BA-013完了条件

1. 実際の監視基盤・通知先を選定する。
2. Stagingで全必須シグナルを取得できることを確認する。
3. critical/warningのテスト通知を実施する。
4. alertからRunbookへ到達できることを確認する。
5. 通知本文へSecret・個人情報が混入しないことを確認する。
6. BA-014負荷試験結果を使ってしきい値を再調整する。
