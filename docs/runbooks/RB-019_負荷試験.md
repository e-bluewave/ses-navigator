# RB-019 負荷試験

## 目的

本番開始前に、匿名化または合成した本番相当データを用いて、RLS・一覧・検索・Bulk処理・締め処理相当の性能と安定性を確認する。

## 現在の判断

2026-08-24時点では、本番想定規模は未定とする。

以下の値を推測でProduction合否基準へ固定しない。

- 同時利用者数
- 1テナント当たり案件件数
- 1テナント当たり技術者件数
- 1テナント当たり会社件数
- 1テナント当たり応募・提案件数
- Production合否とする応答時間・error rateの最終目標

正式値が承認されるまでは、smoke・試験経路確認・計測基盤確認・上限探索は実施できるが、その結果をProductionの性能合格証跡として扱ってはならない。

## 安全条件

- Production環境へ負荷試験を実施しない。
- Productionの個人情報・経歴書本文・契約本文等を試験データへコピーしない。
- Production Secretを使用しない。
- Stagingまたは専用の破棄可能な負荷試験環境を使用する。
- テナント境界・RLSを有効にした実運用相当経路で測定する。

## 必須シナリオ

- 案件一覧
- 案件検索
- 技術者一覧
- 技術者検索
- 会社一覧
- 複数テナント並行アクセス時のRLS境界
- Bulk write
- 月末・締め処理相当の集計または財務処理

## 必須計測

各シナリオで以下を記録する。

- request count / throughput
- p50 / p95 / p99 latency
- error rate
- DB connection usage
- slow SQL
- lock wait / long transaction
- CPU・memory・database capacity（取得可能な範囲）
- job backlog / oldest job age（該当時）

BA-013の監視項目と同じ観測面を用い、正式な負荷基準確定後の実測結果をBA-013のalert threshold調整へ返す。

## 試験段階

1. smoke: 最小負荷でシナリオ・認証・RLS・計測経路が成立することを確認する。
2. baseline: 正式な通常負荷が承認された後に実施する。
3. peak: 正式なピーク負荷が承認された後に実施する。
4. stress: Production合否とは切り離した上限探索として段階的に負荷を増加する。
5. recovery: 負荷低下後に接続・job・latencyが正常へ戻ることを確認する。

## 規模未定期間に実施してよいこと

- smokeシナリオの実装
- 合成データ生成方式の実装
- 負荷試験ツールの候補評価
- p50 / p95 / p99 / error rate / throughputの収集確認
- DB connection・slow SQL・lock・job backlogの観測確認
- RLS境界違反0件の検証
- stressによる技術的な上限探索

これらはProduction合否とは別のエンジニアリング検証として記録する。

## 規模確定時に記録する事項

プロジェクト責任者が以下を承認し、外部の運用記録または承認記録と紐付ける。

- 同時利用者数
- 各主要エンティティの件数
- 通常負荷とピーク負荷
- latency / error rateのProduction合否基準
- 想定業務時間帯と締め処理条件

## BA-014完了条件

1. 本番想定の負荷規模を承認する。
2. 匿名化・合成データセットを作成する。
3. baseline / peak試験をStagingまたは専用環境で実施する。
4. RLS境界違反が0件であることを確認する。
5. 承認済み合否基準内のlatency/error rateであることを確認する。
6. DB connection・slow SQL・lock・job backlogを記録する。
7. BA-013監視しきい値を実測結果で再調整する。
8. ボトルネックと改善内容を記録する。

本番想定規模が未定の間、BA-014は「枠組み実装中」であり「完了」としない。
