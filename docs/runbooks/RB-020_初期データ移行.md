# RB-020 初期データ移行

## 目的

初期データ投入を安全・再実行可能・監査可能に実施し、重複登録や部分投入、誤投入時の復旧不能を防ぐ。

## 基本原則

- Productionへ直接手作業で大量投入しない。
- 本投入前に必ずdry-runを実施する。
- すべての移行実行に一意なrun IDを付与する。
- 再実行しても二重登録を起こさない設計にする。
- 重複判定ルールをデータ種別ごとに明示する。
- 1回の実行で作成・更新・スキップ・失敗した件数を記録する。
- 原本データや個人情報をGitHub、PR、チャット、CIログへ保存しない。
- 本番Secret、DB URL、Project Ref、個人情報を実行証跡へ残さない。

## 移行前準備

1. 対象データ種別と件数を確定する。
2. 移行元ファイルのチェックサムを取得する。
3. 列マッピングと型変換ルールを確認する。
4. 必須項目・参照整合性・コード値変換を検証する。
5. 重複判定キーをデータ種別ごとに定義する。
6. dry-runでcreate / update / skip / reject予定件数を確認する。
7. rollback対象を識別できるrun IDとsource keyを準備する。
8. Stagingで同じ手順を実施する。

## 重複判定

重複判定は曖昧な名称一致だけに依存してはならない。

優先順位は以下とする。

1. 移行元の安定したexternal/source ID
2. テナント内で業務上ユニークなコード
3. 複合自然キー
4. 人手確認が必要な候補

名称、メールアドレス、電話番号等だけで自動統合する場合は誤統合リスクを別途評価する。

各データ種別について、採用した重複キーとその根拠を移行マッピング表へ記録する。

## 再実行

- 同じsource key + 同じrun対象を再投入しても二重INSERTしない。
- 再実行時はcreate / update / skipの判定を決定的にする。
- 同じ入力ファイルを再実行した結果が不必要に変化しないことを確認する。
- 中断後は全件やり直しではなく、未処理または失敗分から安全に再開できることを確認する。
- 部分成功を隠蔽しない。

## 実行単位

1回の移行実行について最低限以下を外部運用記録へ残す。

- run ID
- 実行日時
- 対象環境種別
- 入力ファイルの論理名とチェックサム
- 対象データ種別
- 入力件数
- create件数
- update件数
- skip件数
- reject/error件数
- 実行者または責任者
- rollback可否
- 再実行回数

個人情報本文やSecretは記録しない。

## ロールバック

### 原則

- run IDで当該移行による変更範囲を特定できること。
- 既存業務データを巻き込む全件削除は禁止する。
- rollback前に対象件数をdry-run表示する。
- 親子関係と参照整合性を考慮した順序で戻す。
- 既存行を更新した場合は、更新前値を安全な外部証跡または専用Staging方式で復元可能にする。

### rollbackできない変更

外部送信、メール送信、会計連携等の不可逆な副作用を移行処理に含めない。必要な場合はデータ投入完了後の別工程に分離する。

## Production手順

1. Staging結果と件数差分を確認する。
2. Production用入力チェックサムを確定する。
3. Production向けdry-runを実行する。
4. create / update / skip / reject予定件数を承認する。
5. 本投入を実行する。
6. 件数・参照整合性・RLS境界・代表レコードを確認する。
7. 同じ入力で再実行し、意図しない追加作成が0件であることを確認する。
8. run IDと結果を外部運用記録へ保存する。

## 失敗時

- 入力不備はrejectとして隔離し、正常行へ混入させない。
- 大量の予期しないupdate/deleteが検出された場合は投入を停止する。
- 部分投入が発生した場合はrun ID単位で影響範囲を確認する。
- rollbackまたは修正後再実行のどちらを選んだかを記録する。
- RLS境界違反、別テナント更新、参照破損が1件でもあれば移行失敗とする。

## BA-015完了条件

1. 実際の移行元と列マッピングが確定している。
2. データ種別ごとの重複判定キーが承認されている。
3. Stagingでdry-run、本投入、再実行、rollbackを実証している。
4. 再実行時の意図しない重複作成が0件である。
5. RLS・テナント境界違反が0件である。
6. Production投入前後の件数とエラー証跡が確認されている。
7. rollbackまたは修正再実行手順が実測済みである。
