# RB-016 個人情報匿名化・完全削除

## 目的

SES Navigatorに保存される個人情報について、BA-010の保持期間と整合した匿名化・完全削除、法的要請によるLegal Hold、テナント解約後の削除手順を定義する。

## 基本原則

- 個人データは利用目的の達成に必要な範囲で保持し、利用する必要がなくなった場合はBA-010の方針に従い削除または不可逆匿名化する。
- BA-010で定めた一般個人データの基準である「利用目的終了後90日以内」を上限として運用する。ただし、法令・契約・Legal Holdにより保持根拠が残るデータは対象外とする。
- マスキング、仮名化、soft deleteだけでは完全削除扱いにしない。
- 匿名化を削除代替として扱う場合は、特定個人を識別できず、元の個人情報を復元できないことを確認する。
- Production識別子、個人情報、経歴書本文、メール本文、AI入出力本文をGitHubへ保存しない。

## 匿名化と仮名化の区別

### 不可逆匿名化

削除代替として利用できるのは、次をすべて満たす場合に限る。

1. 氏名、メール、電話番号、住所等の直接識別子を削除する。
2. 社員番号、外部ID、resume ID等のリンク可能な識別子を削除または十分に一般化する。
3. 再識別用の対応表・復号鍵・復元可能な変換情報を保持しない。
4. 他の保有情報と容易に照合して本人を特定できないことを確認する。
5. 匿名化検証結果を個人情報を含まない証跡として残す。

### 削除代替として認めないもの

- 表示上のマスキングのみ
- UUID等への置換だけで対応表が残るもの
- 仮名加工情報の作成のみ
- `deleted_at`等によるsoft deleteのみ
- UIや検索結果から非表示にしただけのもの

これらは元データが残るため、保持期間・アクセス制御・削除対象として引き続き管理する。

## Legal Hold

訴訟、監査、行政・司法機関からの適法な要請、契約紛争等により削除を停止する必要がある場合はLegal Holdを適用する。

必須項目:

- hold ID
- 対象カテゴリまたは対象範囲
- 理由
- 責任者
- 開始日時
- 次回レビュー日時
- 解除日時または状態

運用ルール:

- Legal Holdは通常の削除期限より優先する。
- Hold中のデータは通常利用から可能な限り分離し、必要最小限の担当者だけがアクセスする。
- 無期限Holdをレビューなしで継続してはならない。
- Hold解除後は元の保持期限を再評価し、期限超過済みなら速やかに削除または不可逆匿名化する。
- 要請書面や個人情報そのものを公開GitHubへ保存しない。

## 削除実行フロー

### 1. 対象確定

- deletion request IDを発行する。
- tenant / data subject / retention category等から対象を特定する。
- DB、Storage、派生データ、検索索引、外部連携、バックアップの存在箇所をinventory化する。
- Legal Holdまたは法定保存対象を除外する。

### 2. Dry Run

実削除前に対象件数と対象ストアを確認する。証跡には件数・カテゴリ・期間・内部run IDのみを記録し、個人情報を含めない。

### 3. 本番データ削除

- DBの個人データをhard deleteまたは不可逆匿名化する。
- Storageの経歴書、添付、生成物等を削除する。
- 検索索引、キャッシュ、集計・派生データに本人識別可能情報が残らないことを確認する。
- 外部連携先でSES Navigatorが削除責任を持つコピーがある場合は削除キューへ登録する。

### 4. バックアップ対応

既存バックアップを破壊的に書き換える代わりに、削除対象を示すtombstone/deletion ledgerを保持する。

- backup restore時はledgerを再適用する。
- 復旧検証完了前に削除済みデータを業務利用へ戻さない。
- BA-006/007の保存期間満了により旧バックアップ自体も自然消去されることを確認する。
- ledgerには個人情報本文を保存せず、内部識別子と削除run ID等、必要最小限の情報のみを保持する。

### 5. 検証・証跡

- DBで対象が存在しない、または匿名化済みであることを確認する。
- Storage objectが存在しないことを確認する。
- 派生データ・検索面で再出現しないことを確認する。
- 削除日時、カテゴリ、件数、実行者ロール、結果、検証結果を記録する。
- 証跡自体に個人情報を含めない。

## テナント解約時

1. テナントの新規書込みを停止する。
2. ログイン・API・管理アクセスを失効する。
3. Webhook、OAuth、外部API token等を失効する。
4. DB / Storage / 派生データ / 外部連携コピーをinventory化する。
5. BA-010の保持カテゴリとLegal Holdを適用する。
6. 保持根拠のないデータは利用目的終了後90日以内にhard deleteまたは不可逆匿名化する。
7. 保持根拠が残る契約・請求等はテナント通常アクセスから分離して期限まで保持する。
8. 最終削除後、個人情報を含まない完了証跡を残す。

## 法的要請への対応

- 要請を受けただけで自動削除・自動開示しない。
- 要請の真正性、法的根拠、対象範囲を責任者が確認する。
- 削除停止が必要な場合のみLegal Holdを設定する。
- 開示・提出が必要な場合は最小限の範囲に限定し、別途承認・監査証跡を残す。
- GitHubのRunbookには実案件名、個人名、要請書、提出データを保存しない。

## Staging検証

Production開始前に非本番の人工データで次を確認する。

1. hard deleteでDB行・Storage objectが消える。
2. 不可逆匿名化後に元情報を復元できない。
3. soft deleteのみでは検証PASSにならない。
4. Legal Hold中は削除対象から除外される。
5. Hold解除後は期限に従い削除される。
6. restore後にdeletion ledgerを再適用すると削除済みデータが再出現しない。
7. 削除証跡に個人情報が含まれない。

## BA-011完了条件

GitHub上のRunbook・policy・CIのみでは完了扱いにしない。次をすべて満たした時点で完了とする。

1. Productionの個人情報ストアがinventory化されている。
2. 各ストアのhard delete / 匿名化方式が確定している。
3. Legal Holdの責任者・運用台帳が確定している。
4. テナント解約フローが実環境運用へ組み込まれている。
5. StagingでDB・Storage・派生データ・restore後再削除を検証済み。
6. privacy ownerとtechnical ownerが承認している。
