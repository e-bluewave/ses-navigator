# RB-022 長時間処理・外部ワーカー境界

## 1. 目的

BA-017として、Supabase Edge Functionsで扱う同期処理と、キュー／外部ワーカーへ移行する長時間処理の境界を定義する。

## 2. 現行プラットフォーム制約

Supabase hosted Edge Functionsにはメモリ、CPU、wall-clock、idle timeout等の上限がある。2026-08-24時点の公式Docsでは、最大メモリ256MB、wall-clockはFree 150秒／Paid 400秒、request idle timeout 150秒である。上限値そのものをアプリの通常処理予算として使わず、十分な余裕を持つ。

参考: https://supabase.com/docs/guides/functions/limits

## 3. Edge Functionで扱う処理

次をすべて満たす処理を原則としてEdgeで扱う。

- request/response型で完了時間が明確に限定される
- 通常時の想定実行時間が30秒以内
- CPU集約処理ではない
- 大容量ファイル変換を行わない
- 途中再開を必要としない
- 冪等性または安全な再試行方式がある
- タイムアウト時に業務データが中途半端な状態にならない

## 4. 外部ワーカーへ移す処理

次のいずれかに該当する場合は、Edge同期処理から分離し、ジョブ＋外部ワーカー方式を使う。

- 通常時に30秒超が見込まれる
- CPU集約処理
- 大量レコードの一括処理
- 大容量ファイル解析・変換
- 多数のAI呼び出しを伴うバッチ
- 経歴書／スキルシート等の大量解析
- 大規模エクスポート／インポート
- 長時間の外部API待機
- 途中再開、進捗、キャンセルが必要
- retry/backoffやDead Letter管理が必要

## 5. ジョブ設計

長時間処理は最低限次を持つ。

- job_id
- tenant_id
- job_type
- status
- idempotency_key
- attempt_count
- max_attempts
- next_attempt_at
- locked_at / lease期限
- progress
- created_at / started_at / completed_at / failed_at
- エラー分類。ただしSecret・個人情報・原文をログへ出さない

## 6. 再試行

- retry対象と恒久エラーを区別する。
- retryは指数バックオフ等の遅延を入れる。
- 同じjobの重複実行を防ぐ。
- 再実行しても二重請求、二重メール、二重登録等が起きないよう副作用単位で冪等性を確保する。
- 最大試行回数を超えたjobはDead Letter相当の状態へ遷移し、人が確認できるようにする。

## 7. 監視

BA-013の監視と接続し、少なくとも次を監視する。

- queued件数
- 最古queued時間
- running時間
- retry件数
- failure件数
- dead-letter件数
- lease期限切れ件数
- job種別ごとの処理時間

## 8. セキュリティ

- Production Secretをjob payloadへ直接格納しない。
- job payloadに不要な個人情報を入れない。
- tenant境界をjob取得・処理・結果保存で維持する。
- 外部ワーカーの認証情報は環境別Secret管理とする。
- 実payload、個人情報、Project Ref、credentialをGitHubやCIログへ保存しない。

## 9. 完了条件

BA-017の実装完了は、Edge／worker境界、ジョブ再試行、冪等性、Dead Letter、監視要件をポリシーとCIで固定すること。実運用完了には、採用するworker／queue実装でStagingの成功・retry・timeout・worker停止・再開試験を行う。
