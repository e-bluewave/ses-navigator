# RB-007 環境分離・昇格

## 1. 目的

SES NavigatorのLocal、CI、Staging、Productionを分離し、同一のSupabase Project、Vercel Project、Secret、実データを誤って共有しないための運用基準と昇格手順を定義する。

## 2. 環境境界

| 環境 | Supabase | Vercel | データ | 用途 |
| --- | --- | --- | --- | --- |
| Local | Supabase CLIローカル | 使用しない | 固定Seed・架空データ | 開発・単体確認 |
| CI | 実行単位の一時環境 | 使用しない | 実行ごとに初期化 | 自動回帰 |
| Staging | 専用Project | 専用Project | 架空データ | 統合・E2E・リリース確認 |
| Production | 専用Project | 専用Project | 実業務データ | 本番運用 |

StagingとProductionは、Supabase ProjectとVercel Projectの両方を必ず別Projectにする。同じProjectを環境変数だけで切り替えて共用しない。

環境固有のProject ID、Project Ref、URL、Secret値はGitHubへ保存しない。GitHubでは分離ルール、変数名、検証手順だけを管理する。

## 3. Secretと環境変数

- Local、Staging、ProductionでSecretを共有しない。
- ProductionのSecretをStaging、CI、Localへコピーしない。
- VercelのProduction環境変数とPreview環境変数を明示的に分離する。
- SupabaseのPublishable/Anon系公開キーを除き、Secret key、Service Role、DB password等をブラウザへ渡さない。
- 環境別Secret台帳はRB-006に従い、アクセス制御された運用保管先で管理する。

## 4. データ境界

- ProductionデータをLocalへコピーしない。
- ProductionデータをStagingへ通常コピーしない。
- 本番相当データが必要な検証は、架空データまたは匿名化済みデータを使う。
- 例外的に本番由来データをStagingへ持ち込む場合は、匿名化、最小化、期限付き削除、承認、削除確認を必須とする。

## 5. デプロイ昇格

通常の昇格順序は次のとおりとする。

1. Localで実装・単体確認
2. CIでformat、lint、typecheck、test、security check、buildを成功させる
3. `Main`へ承認済みPRをマージ
4. 同一Commit SHAをStagingへ反映
5. StagingでMigration、Auth、主要API、Data API境界、重要E2Eを確認
6. Production反映を承認
7. Stagingで確認した同一Commit SHAをProductionへ昇格
8. Productionで読み取り中心のSmoke testを実施
9. Commit SHA、Migration番号、実施者、結果を秘密値なしで記録

Stagingで未確認のCommitをProductionへ直接デプロイしない。

## 6. DB Migration

- MigrationはGitHub `Main`を正本とする。
- Localで作成した新規MigrationをStagingへ先に適用し、成功後にProductionへ同じ順序で適用する。
- 過去Migrationを環境別に書き換えない。
- StagingとProductionでMigration番号と内容が分岐した場合はProduction反映を停止する。
- DBの緊急変更をDashboard/SQL Editorで実施した場合は、同等MigrationをGitHubへ戻す。

## 7. 初回環境作成チェックリスト

### Staging

- 専用Supabase Projectを作成
- 専用Vercel Projectを作成
- Productionとは異なるProjectであることを確認
- Staging専用Secretを発行
- `Main`からMigrationを適用
- 架空Seedだけを投入
- Auth redirect URL、Data API公開スキーマ、Storage、MFA、メール設定を確認
- `pnpm security:env-separation`の実環境バインド検査を実行
- Data API / Auth smoke testを実行

### Production

- Stagingとは別のSupabase Projectを作成
- Stagingとは別のVercel Projectを作成
- Production専用Secretを発行
- Stagingで確認済みのMigrationとCommit SHAだけを昇格
- Production用Auth redirect URL、Data API公開スキーマ、Storage、MFA、メール設定を確認
- 読み取り中心のSmoke testを実施

## 8. 実環境バインド検査

環境固有値はコマンド実行時だけ環境変数で渡し、GitHubへ保存しない。

対象変数名:

- `SESN_STAGING_SUPABASE_URL`
- `SESN_PRODUCTION_SUPABASE_URL`
- `SESN_STAGING_VERCEL_PROJECT_ID`
- `SESN_PRODUCTION_VERCEL_PROJECT_ID`

4項目を設定して次を実行する。

```bash
pnpm security:env-separation
```

StagingとProductionで同じSupabase URLまたはVercel Project IDが設定されている場合は失敗させる。

## 9. ロールバック

- アプリは直前の正常なCommit SHAへ戻す。
- DBはDown Migrationを前提にせず、前方修正またはバックアップ復元を選択する。
- Production障害時にStagingのDBやSecretをProductionへ流用しない。
- 切り戻し後も環境境界を維持し、原因調査のためにSecret値や実データをGitHubへ記録しない。

## 10. 完了条件

BA-001は次を満たした時点で完了とする。

1. StagingとProductionが別Supabase Projectで作成されている。
2. StagingとProductionが別Vercel Projectで作成されている。
3. 環境別Secretが分離されている。
4. Local / CI / Staging / Productionの昇格手順が確定している。
5. `pnpm security:env-separation`が静的検査と実環境バインド検査でPASSする。
6. Stagingへ`Main`の同一Commit SHAを反映し、主要Smoke testがPASSする。

GitHub側の設計・CIガード完了だけではBA-001を完了扱いにせず、実環境Project分離の確認後に完了へ更新する。
