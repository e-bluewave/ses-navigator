# RB-008 Authアカウントライフサイクル

## 1. 目的

Supabase AuthとSES Navigatorの業務プロフィール・所属・権限を分離したまま、利用開始、MFA、利用停止、退職、管理者権限失効、セッション強制失効、再開を安全に実施する。

## 2. 原則

- 認証IDの正本はSupabase Authの`auth.users`とする。
- 業務利用可否はSES Navigator側の有効なプロフィール、所属、ロール、権限、RLSで判断する。
- Authアカウント削除を通常の利用停止手段にしない。
- 利用停止・退職・管理者失効では、業務権限の無効化を先に行い、その後にAuthセッションを失効する。
- 管理者はAAL2を必須とし、TOTP登録・検証済みでなければ管理機能を利用させない。
- Service Role、Secret key、JWT、メールアドレス、パスワードをIssue、PR、チャット、ログへ保存しない。
- Auth管理操作はProductionとStagingを明確に区別し、対象環境と対象ユーザーを二重確認する。

## 3. 状態と扱い

| 状態 | Authアカウント | 業務プロフィール・所属 | セッション | 用途 |
| --- | --- | --- | --- | --- |
| 招待前 | なし | 必要に応じて準備 | なし | 利用開始前 |
| 招待済み | あり | 有効化準備中 | 初回認証待ち | 初回利用開始 |
| active | あり | 有効 | 有効 | 通常利用 |
| suspended | 原則保持 | 無効化 | 強制失効 | 一時停止 |
| retired | 原則保持 | 在籍終了・権限無効 | 強制失効 | 退職・契約終了 |
| deleted | 削除可 | 保持/匿名化方針に従う | 失効 | 法的・保持期限対応後 |

## 4. 新規利用開始

1. 対象テナント、組織、ロール、権限を確認する。
2. Productionでは公開サインアップを使用せず招待制とする。
3. 招待先を管理画面上で確認し、秘密情報を運用記録へ転記しない。
4. 招待リンク受諾後にパスワードを設定する。
5. 管理者ロールの場合はTOTPを登録し、AAL2へ到達させる。
6. `GET /api/v1/auth/context`でMFA必須判定が想定どおりであることを確認する。
7. 対象業務画面へアクセスでき、対象外権限が拒否されることを確認する。

## 5. 一時停止

一時停止ではAuthユーザーを削除しない。

1. 対象ユーザー、テナント、理由、実行者を確認する。
2. SES Navigator側の利用状態を停止し、所属・割当・共有・ロールの有効性を見直す。
3. 管理者権限を持つ場合は`user.manage`、`role.manage`等の管理権限を先に失効する。
4. Supabase Auth側で対象ユーザーのセッションを失効する。
5. 既存ブラウザでAPIアクセスが401/403または業務RLS拒否になることを確認する。
6. 新規ログインが許可されない運用状態であることを確認する。
7. 秘密値を含まない監査・運用証跡を記録する。

## 6. 退職・契約終了

1. 終了日時を確定する。
2. 所属の有効期間を終了し、ロール・権限・担当・共有を無効化する。
3. 管理者権限を最優先で失効する。
4. セッションを強制失効する。
5. 外部連携の個人OAuth token等がある場合は別Runbookに従い失効する。
6. 業務データの作成者・履歴・監査ログは削除せず、参照整合性を維持する。
7. Authユーザーの削除は保持期間・法的要件・BA-010/BA-011の確定後に別工程で判断する。

## 7. 管理者権限失効

管理者権限だけを外す場合でも、古いセッション上の状態を信用しない。

1. DB上の管理者ロール/権限を無効化する。
2. `GET /api/v1/auth/context`の結果が管理者要件を反映することを確認する。
3. 必要に応じて全セッションを失効し、再ログインさせる。
4. 管理画面・管理API・限定RPCへのアクセスが拒否されることを確認する。
5. 監査ログへ実行者、対象、理由、時刻、結果を残す。

## 8. セッション強制失効

対象例：端末紛失、パスワード漏えい疑い、退職、権限昇格誤り、不審アクセス。

1. 先に業務権限を縮小または停止する。
2. Supabase Auth管理機能で対象ユーザーのセッションを失効する。
3. 必要ならパスワード再設定を要求する。
4. 不審なMFA Factorがある場合は正当性確認後に解除・再登録する。
5. 旧Access Token/Refresh Tokenが再利用できないことを確認する。
6. 新しい認証状態で必要最小限の業務アクセスだけが成功することを確認する。

## 9. 再開

1. 停止理由が解消していることを確認する。
2. 必要な所属・ロール・権限だけを再有効化する。
3. 新規ログインを実施する。
4. 管理者はAAL2を再確認する。
5. 対象機能のSmoke testを行う。
6. 再開理由と承認者を証跡へ残す。

## 10. 緊急時

漏えい・侵害疑いでは通常順序より封じ込めを優先する。

1. 対象ユーザーの業務権限を停止する。
2. セッションを即時失効する。
3. 必要に応じてパスワード再設定とMFA再登録を行う。
4. Tenant越境、データ変更、Secret取得の有無を監査する。
5. 関連Secret漏えいが疑われる場合はRB-006/RB-007へ切り替える。

## 11. 検証

既存の自動検証を利用する。

```text
pnpm test
pnpm smoke:auth-project:check
pnpm security:data-api:all:check
pnpm security:client-secrets
```

実環境では、専用の非Productionユーザーで次を確認する。

- active時にログインと許可済みAPIが成功する。
- 管理者はAAL1で業務画面がブロックされ、AAL2で許可される。
- 停止後に既存セッションで業務APIが利用できない。
- 管理者失効後に管理操作が拒否される。
- 再開後に必要最小限のアクセスだけが復旧する。

## 13. BA-003完了条件

- 管理者MFAが実装済みでAAL2必須境界がテストされている。
- 招待・回復・パスワード更新フローが実装済みである。
- 停止、退職、管理者失効、セッション失効、再開の手順が本Runbookで確定している。
- 非Production専用ユーザーで停止→旧セッション拒否→再開の訓練を実施している。
- 管理者権限失効後の管理操作拒否を確認している。
- 秘密情報を含まない証跡が保存されている。

上記の実環境訓練まで完了した時点でBA-003を完了扱いにする。
