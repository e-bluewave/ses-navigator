# 08 テーブル設計

SESN (System Engineer Sales Navigator)

> Vercel + Supabaseを前提とする物理DB・テーブル設計の確定版。PostgreSQL、Supabase Auth、Row Level Security、Supabase Storageを利用する。

---

## 1. 基盤構成

- Web/API: Vercel上のNext.js、Route Handlers、Server Actions
- DB: Supabase PostgreSQL
- 認証: Supabase Auth。`auth.users`を認証IDの正本とする
- 認可: RLSを全業務テーブルで有効化し、ロール・組織・担当・共有・項目権限を評価
- ファイル: Supabase StorageのPrivate Bucket。署名URLを利用
- 非同期処理: 共通`jobs`テーブル、Edge Functions、`pg_cron`をMVP基盤とし、長時間処理は外部ワーカーへ移行可能とする
- マイグレーション: Supabase CLIのSQLをGitHubで管理し、本番Dashboardでの手動DDL変更を禁止

## 2. 命名・型・共通列

- テーブル名・列名: 複数形の`snake_case`
- API JSON: `camelCase`
- 主キー: アプリ側で生成するUUID v7。`auth.users.id`はSupabase AuthのUUIDをそのまま利用
- 文字列: 原則`text`。最大長が業務制約となるコード等のみ`varchar(n)`
- 日時: `timestamptz`、日付のみ`date`
- 金額: 用途別に`numeric(15,2)`または円確定額の`bigint`を使用。通貨はISO 4217コード
- 割合・業務スコア: 固定小数。機械学習内部値のみ`double precision`を許可
- 状態: `text`または`varchar`とCHECK制約。頻繁に追加する業務区分はマスタ化
- 値なし: 原則NULL。空文字列は保存前に項目ルールで検証

主要業務テーブルの共通列:

```sql
id uuid primary key,
tenant_id uuid not null,
management_no varchar(32),
created_at timestamptz not null,
created_by uuid,
updated_at timestamptz not null,
updated_by uuid,
row_version bigint not null default 1,
deleted_at timestamptz,
deleted_by uuid,
delete_reason text
```

- 管理番号は`unique (tenant_id, management_no)`とし、論理削除後も再利用しない
- 検索対象の氏名、会社名、メール、電話等には正規化列を持つ
- `tenant_id + id`の複合一意制約と複合外部キーによりテナント越境をDBでも防止

## 3. テナント・認証・組織・権限

### 3.1 中核テーブル

- `user_profiles`: `user_id`をPK兼`auth.users.id`へのFKとする。テナント非依存のグローバルプロフィールとし、テナント・組織所属は保持しない
- `tenants`: 契約企業。`trial / active / suspended / terminated`
- `tenant_memberships`: 複数テナント所属、在籍期間、デフォルト所属。`(tenant_id, user_id)`を参照候補キーとする
- `organizations`: `parent_id`による階層。同一テナントの親組織だけを複合外部キーで許可する
- `organization_memberships`: 複数組織所属、主所属、役職、有効期間。同一テナントのユーザー・組織だけを許可する
- `roles`: 標準ロールとテナント独自ロール
- `permissions`: `resource.action`形式。Migration 009時点の権限カタログは56件
- `role_permissions`: allowのみ。未設定は拒否。同一テナントのロールだけを許可する
- `user_roles`: サロゲートキー`id`を持ち、テナント・任意の組織スコープ・有効期間・失効情報を保持する
- `system_admins`: テナントロールと分離
- `record_shares`: ユーザーまたは組織に対する期限付きの明示共有。`view / comment / edit`を許可し、テナント越境を複合外部キーで防止する

`system_admin`は`system_admins`で別管理する。テナント標準ロールは`tenant_admin / sales_manager / sales / engineer_support / legal / accounting / approver / viewer`とする。

### 3.2 RLS

- 通常条件は`tenant_id = current_tenant_id()`かつ`deleted_at is null`
- INSERTは`WITH CHECK`でアクティブテナント一致を検証
- UPDATEは`USING`と`WITH CHECK`の両方を設定
- 通常ユーザーへ物理DELETE権限を付与しない
- 項目単位の秘匿は限定ビュー、RPC、API整形を併用
- Service Roleは管理処理、ジョブ、Webhook、移行等に限定し、処理内でもテナントと権限を明示検証
- RLSヘルパー関数は`SECURITY DEFINER`を慎重に使い、`search_path`固定、PUBLIC実行権限削除を必須とする

Migration 109〜112の実装では、`app`の102テーブルと`audit`の2テーブル、合計104テーブルでRLSを有効化・強制している。Migration 112はMigration 110の一律テナントPolicyを置き換え、次の順で認可する。

1. System Admin
2. テナント所属と機能権限
3. テナント全体または組織・配下組織のロールスコープ
4. 主担当、作成者、割当ユーザー・割当組織
5. 有効な`record_shares`
6. 親レコードの権限を継承する子テーブル

通常ユーザー向けDELETE Policyは作成せず、物理DELETEはGRANTでも禁止する。`audit.task_status_histories`は親タスクの参照権限を継承し、`audit.audit_logs`は`audit.read`権限を要求する。

## 4. 会社・担当者・技術者

### 4.1 会社

- `companies`: 会社本体、法人番号、正規化名称、住所、リスク概要、状態、主担当、所有組織
- `company_roles`: customer、business_partner、engineer_employer、end_customer、prime_contractor等。期間管理
- `company_risk_records`: リスク種別、重要度、公開範囲、有効期間
- `company_contacts`: 会社単位の担当者、主担当、所有組織。MVPでは同一人物でも会社ごとに別行
- `company_contact_histories`: 部署、役職、連絡先の変更履歴
- `company_duplicate_candidates`: スコアと判定根拠、人による判断結果

### 4.2 技術者

- `engineers`: 現在の公開基本情報、基本状態、稼働可能状態、主担当、所有組織
- `engineer_private_details`: 生年月日、個人メール、電話、住所等の機密情報
- `engineer_affiliations`: 所属会社・契約形態の履歴
- `engineer_preferences`: 希望単価、勤務地、リモート、稼働条件の履歴
- `engineer_preferred_locations`、`engineer_preferred_contract_types`: 検索用中間テーブル
- `skills`、`skill_aliases`: 共通スキルとテナント独自スキル
- `engineer_skills`: 経験月数、習熟度、最終利用日、根拠、検証状態
- `engineer_career_histories`、`career_history_skills`: 構造化職務経歴
- `engineer_resumes`、`engineer_resume_versions`: 経歴書本体と版
- `resume_extraction_results`: AI抽出候補。承認後に正式反映
- `engineer_duplicate_candidates`、`engineer_merge_jobs`、`engineer_merge_histories`: 重複確認と安全な統合

## 5. 案件

- `projects`: 案件本体の現在情報、案件状態、募集状態、主要顧客、主担当、所有組織
- `project_sources`、`project_source_versions`: 複数受領元、提示条件、商流原文、版
- `project_company_relations`: 元請、上位、顧客、エンド等を`commercial_order`付きで管理
- `project_positions`: 募集ポジション。提案は必ずポジションを参照
- `project_requirements`、`project_requirement_versions`: 要件と版
- `project_skills`、`project_position_skills`: 必須・尚可、要求レベル、経験月数、重み
- `project_work_conditions`: 勤務場所、リモート、時間等の履歴
- `project_contract_conditions`: 契約・単価・精算条件の履歴
- `project_assignments`: 主担当、副担当、支援、閲覧
- `project_duplicate_candidates`、`project_merge_jobs`、`project_merge_histories`
- `project_extraction_results`: メール・添付からのAI抽出候補

案件本体と受領経路は分離し、同一案件を受領元ごとに複製しない。

## 6. 提案・承認・送信・面談

- `proposals`: 案件ポジション、技術者、提案先、単価、経歴書版、要件版、現在状態、主担当、所有組織
- `proposal_snapshots`: 作成・承認・送信時点の再現用スナップショット
- `proposal_status_histories`: 全状態変更、理由、主体、訂正、KPI除外
- `proposal_outcomes`: 面談依頼、見送り、辞退、成約等の構造化結果
- `approval_requests`、`approval_steps`: 提案・契約等で共用。将来の多段承認に対応
- `outbound_messages`、`message_recipients`、`message_versions`、`message_delivery_attempts`
- `proposal_message_links`: 1通のメールと複数提案を多対多で関連
- `message_attachments`: 送信時のファイル版を固定
- `interviews`: 提案配下に回ごとに作成
- `interview_participants`、`interview_schedule_candidates`、`interview_schedule_responses`
- `interview_evaluations`: 顧客評価、社内評価等を評価元別に保存
- `proposal_transition_suggestions`: 面談結果から状態変更候補を作り、人が確定

再提案、訂正メール、面談再調整は元データを上書きせず、新規行と関連IDで追跡する。

## 7. 契約・参画

- `contracts`: 現在の主要条件、状態、元提案または移行元
- `contract_versions`、`contract_terms`: initial、amendment、renewal、correctionの版管理
- `contract_status_histories`、`contract_price_histories`
- `contract_parties`: 売手、買手、BP、元請、エンド等
- `contract_signatures`: 電子契約サービス連携
- `contract_renewal_candidates`: 更新確認中の候補
- `engagements`: 契約配下の参画。1契約に複数参画を許可
- `engagement_status_histories`、`engagement_conditions`
- `engagement_checklists`、`engagement_checklist_items`: 開始前必須確認
- `engagement_end_records`: 終了理由、評価、引継ぎ
- `engagement_followups`: 月次フォロー
- `engagement_incidents`: 機密な問題・インシデント

契約更新と再参画は新しい本体行を作り、前レコードIDで連結する。

## 8. 月次実績・請求・入金・支払

- `engagement_monthly_results`: 1参画×1対象月。対象月は月初日の`date`
- `monthly_result_versions`、`engagement_daily_work_records`
- `monthly_result_extraction_results`: AI・ファイル抽出候補
- `monthly_sales_calculations`、`monthly_cost_calculations`: 計算根拠と版を保存
- `accounting_periods`: 売上締め、請求締め、支払締めを分離
- `billing_destinations`: 請求先の履歴
- `invoices`、`invoice_lines`: 複数参画・複数月の集約を許可
- `payments_received`、`payment_allocations`: 入金と請求の多対多消込
- `partner_payments`、`partner_payment_lines`
- `supplier_invoices`: BP受領請求書と支払予定の照合
- `accounting_export_batches`、`accounting_export_lines`

締め後は通常編集を禁止し、理由・承認・影響確認を伴う再開または訂正伝票のみ許可する。適格請求書の発行者情報、登録番号、税率別集計は発行時点でスナップショット保存する。

## 9. 共通基盤

### 9.1 ファイル・コメント・タグ

- `files`、`file_versions`、`file_links`
- `file_scan_results`: cleanになるまで利用・ダウンロード・AI解析を禁止
- `file_processing_jobs`、`file_processing_results`
- `comments`、`comment_links`、`comment_versions`、`comment_mentions`
- `comments.visibility = 'organization'`では`organization_id`を必須とし、同一テナントの有効な所属組織だけを許可する
- `tags`、`tag_links`、タグ統合履歴

Storageパスは`private/{tenant_id}/{resource_type}/{resource_id}/{file_id}/{version_id}`を基本とし、元ファイル名を使用しない。

### 9.2 通知・タスク

- `notifications`、`notification_recipients`、`notification_deliveries`
- `user_notification_preferences`
- `tasks`、`task_assignments`、`task_links`、`task_status_histories`
- 通知・自動タスクには`deduplication_key`を持つ

### 9.3 監査・ジョブ・AI・Webhook

- `audit.audit_logs`: 追記専用。通常ロールのUPDATE・DELETE禁止
- `jobs`、`job_attempts`、`job_events`、`job_results`: リース方式で多重実行を防止
- `ai_executions`、`ai_execution_inputs`、`ai_execution_outputs`、`ai_execution_reviews`、`ai_execution_feedback`
- `webhook_subscriptions`、`webhook_deliveries`、`webhook_delivery_attempts`
- `idempotency_records`: テナント・主体・操作・キー単位
- `saved_searches`

### 9.4 メール・営業活動・外部連携

- `inbound_messages`、`mailboxes`、`mailbox_members`、`message_threads`、`message_thread_links`
- `sales_activities`、`sales_activity_links`、活動参加者
- `evaluation_schemes`、`evaluation_items`、`evaluation_levels`、`evaluations`、`evaluation_scores`
- `reason_codes`、`master_definitions`、`master_values`
- `integration_accounts`、`external_resource_mappings`、`integration_sync_runs`、`integration_sync_items`
- `import_batches`、`import_rows`、`export_requests`
- `service_accounts`、`service_account_roles`、`api_keys`
- `tenant_settings`、`system_settings`、設定変更履歴
- `feature_flags`、`tenant_feature_flags`

OAuthトークン、Webhook Secret、APIキー平文はDBへ保存しない。外部Secret管理または暗号化保管を利用する。

## 10. 制約・トランザクション

- 業務必須列へ`NOT NULL`
- 金額、率、期間、状態へCHECK制約
- 通貨一致時のみ粗利を計算し、売上0の場合は粗利率NULL
- 重複不可の有効期間を排他制約またはトランザクション内DB関数で検証
- 外部キー削除は業務本体`RESTRICT`、純粋な子・中間`CASCADE`、任意の作成者等`SET NULL`
- 採番は`FOR UPDATE`で採番行をロックし、欠番を許容、番号を再利用しない
- 状態変更は本体、状態履歴、監査、Outboxを同一トランザクションで保存
- `outbox_events`をTransactional Outboxとして利用し、通知・Webhook・外部同期を非同期配信
- 長時間トランザクションを禁止し、大量処理はチャンク化
- `row_version`を全更新で検証
- 悲観ロックは採番、締め、入金消込等に限定
- 複数対象の更新順序を規約化し、デッドロックは限定回数再試行

## 11. インデックス・検索

- 全外部キー列へ原則インデックス
- 業務検索用複合インデックスは原則`tenant_id`を先頭
- 通常検索は`where deleted_at is null`の部分インデックス
- 状態＋更新日時、担当＋状態、期限、RLS判定列、正規化列を用途ベースで設計
- JSONB・全文検索用GINは実利用箇所だけに作成
- MVPの日本語検索は正規化列＋`ILIKE`＋限定的全文検索
- `pgvector`を導入可能な構造とするがMVP必須にはしない
- 権限キャッシュ、パーティション、マテリアライズドビューは性能計測後に導入判断

## 12. スキーマ・Data API公開範囲

### 12.1 スキーマ

- `app`: 業務テーブル、権限テーブル、RLSヘルパー。Data API対象はGRANTで個別制御する
- `master`: 参照マスタ。現時点でテーブルなし
- `private`: Migration専用関数、内部処理。Data APIへ公開しない
- `audit`: 監査ログとタスク状態履歴。Data APIへ直接公開しない
- `integration`: 外部連携用。Data APIへ直接公開しない
- `reporting`: 限定ビュー・集計用。ビュー作成後に個別公開する
- `public`: Supabase既定オブジェクト用。業務テーブルは配置しない

### 12.2 Migration 112適用後の公開状態

- `app`および`audit`の全104テーブルでRLSは有効かつ強制
- `app`・`audit`スキーマへの`USAGE`、テーブルへの`SELECT / INSERT / UPDATE`のData API用GRANTは未作成
- `anon`には業務テーブル権限なし
- `authenticated`にはRLS評価用21関数の`EXECUTE`だけを明示付与済み
- 5個の補助・Trigger関数にはPostgreSQL既定の`PUBLIC EXECUTE`が残っているため、Migration 113で明示的に削除する
- `supabase/config.toml`のData API公開は`public`・`graphql_public`だけ、追加search_pathは`public`・`extensions`だけに固定する
- `pnpm security:supabase-config`でローカル設定を検証し、`SESN_REMOTE_EXPOSED_SCHEMAS`を指定した場合はDashboard実値との一致も検証する

したがって、GitHub管理上のData API公開は限定View・RPCを置く`public`に閉じている。Dashboardで`app`・`audit`・`private`等が追加されていないことは、環境ごとに設定スナップショットをガードへ渡して確認する。

### 12.3 Migration 113 GRANT対象マトリクス

記号は`S=SELECT`、`I=INSERT`、`U=UPDATE`、`X=EXECUTE`、`A=ALL`、`—=付与なし`とする。RLSはGRANTに加えて常に適用する。

|対象|`anon`|`authenticated`|`service_role`|公開方式|
|---|---:|---:|---:|---|
|`app`スキーマ|—|`USAGE`|`USAGE`|SupabaseのExposed schemas設定を別途確認|
|`audit`スキーマ|—|—|`USAGE`|限定View/RPCのみ|

|案件の通常情報 039〜040、042〜051|—|S|A|書き込みは業務API/RPC|

Migration 113では`PUBLIC`と`anon`からカスタムスキーマ・テーブル・関数権限を明示的にREVOKEする。`authenticated`へのデフォルト権限は設定せず、新規オブジェクトは必ず個別レビューする。`service_role`へのデフォルト権限だけをMigration所有者単位で設定する。

RLSは行単位の制御であり、同じ行の機密列を隠せない。技術者機密、経歴書原文、案件受領原文、契約、財務、AI入出力、監査、Webhookはベーステーブルへ直接GRANTせず、Migration 114の限定Viewまたは専用RPCを経由する。

## 13. バックアップ・削除・運用

- Supabase標準バックアップに加え、外部への定期論理バックアップを実施
- StorageオブジェクトはDBと別に外部バックアップ
- 別環境への復旧訓練を定期実施
- 通常の論理削除と、法的要請による匿名化・完全削除を分離
- テナント解約は利用停止、エクスポート猶予、保持、匿名化・削除の段階方式
- 遅いクエリ、接続数、容量、ロック、RLS負荷を継続監視
- 保存期間、RPO、RTOの具体値は本番開始前のP0課題として確定

## 14. DDL作成順序

1. スキーマ、拡張、共通関数
2. テナント、ユーザー、組織、権限
3. 共通マスタ、会社、担当者、技術者
4. 案件、提案、承認、メッセージ、面談
5. 契約、参画、月次実績、請求、入金、支払
6. 共通ファイル、コメント、通知、タスク、監査、ジョブ、AI、外部連携
7. インデックス、RLS、限定ビュー、RPC
8. 冪等Seed、RLS自動テスト、主要トランザクションテスト
